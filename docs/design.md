# 設計の判断

開発中に迷ったところを、「課題 → 検討した案 → 決めたこと → 理由」の形で残します。

## 1. すりガラスの表現: OS のぼかし効果を使わず、擬似ガラスにした

- **課題**: カードの形をした、半透明でぼかしの入ったパネルを、壁紙の上に出したい。
- **検討した案**:
  1. OS のアクリル効果
  2. Mica
  3. ブラー
  4. 擬似ガラス（壁紙を自分でぼかし、カードの背景に敷く）
- **実機で見た結果**（Windows 11 25H2）:
  - アクリル・Mica・ブラーは、どれも窓全体に均一にかかり、カードの形にならなかった。
  - Mica は、壁紙がほとんど透けなかった。
  - 効果なしでは、デスクトップのアイコンが文字に重なって読めなかった。
- **決めたこと**: 擬似ガラス。
  - 壁紙のパスと表示方法（塗りつぶし・調整・中央など）をレジストリから読む。
  - モニターの大きさに合わせて一度だけ描き、ぼかして画像にする。
  - 窓の位置から、各カードの背景の位置を計算して合わせる。
- **理由**: カードの形に合わせられ、重い処理も起動時の1回だけで済むから。窓を動かしてもぼかし直さない。
- **残る制約**: 壁紙以外（ほかの窓など）は透けない。デスクトップの上のガジェットなので、背後に来るのは基本的に壁紙だけで、問題にならない。

## 2. Win+D でも消さない: 埋め込みではなく、窓の持ち主をデスクトップにした

- **課題**: 「デスクトップの表示」（Win+D）で、ほかの窓と一緒に隠れてしまう。
- **検討した案**:
  1. 窓を常に最背面に置くだけ
  2. 壁紙の層（WorkerW）に子の窓として埋め込む
  3. 窓の持ち主（owner）をデスクトップの窓（Progman）にする
- **決めたこと**: 案3。あわせて、窓を非アクティブにし（`WS_EX_NOACTIVATE`）、常に最背面に置く。
- **理由**:
  - 案1は、Win+D で隠れる（Rainmeter でも同じ報告がある）。
  - 案2は、窓がマウス操作を受け付けなくなり、ドラッグや設定ボタンが使えない。Windows 11 24H2 以降は、デスクトップの窓の構造が変わったという報告もある。
  - 案3なら、操作できるまま残せる。
- **保険**:
  - Windows の版によって効かない場合に備え、見張りのスレッドが0.5秒ごとに確かめる。隠されたり最小化されたりしていれば表示し直し、外れたスタイルは付け直す。
  - 設定で「通常の窓（最背面）」に戻すこともできる。
- **代償**: 非アクティブの窓はキーボード入力を受けないため、文字を入れる設定（地名検索など）は別の窓の設定画面で行う。

## 3. GPU 使用率: Task Manager と同じ定義にそろえた

- **課題**: 「GPU 使用率」の定義はいくつもある。また、内蔵（Iris Xe）と外付け（GTX 1650 Ti）の2枚がある。
- **決めたこと**:
  - 性能カウンター `GPU Engine(*)\Utilization Percentage` を読む。
  - インスタンス名（`pid_…_luid_…_phys_…_eng_…`）を解析し、アダプター（LUID）と処理エンジンごとに、全プロセスの値を合計する。
  - そのうち最大のエンジンの値を、そのアダプターの使用率とする。
  - アダプター名は DXGI で取り、LUID で突き合わせる。
- **理由**:
  - 利用者が見比べるのは Task Manager なので、定義を合わせないと「値が違う」と感じてしまう。
  - ベンダー専用のライブラリ（NVML など）を使わずに、どのベンダーの GPU でも同じ方法で取れる。
- **検証**: 実機で、Task Manager の GPU 0 と GPU 1 と照合した。

## 4. GPU 温度: 使っていない GPU は読まない

- **課題**: ノート PC の外付け GPU は、使っていないときは休止している。温度を読みに行くと休止から起こしてしまい、電池を減らすおそれがある。
- **決めたこと**:
  - 温度は D3DKMT（`KMTQAITYPE_ADAPTERPERFDATA`）で読む。Task Manager と同じ仕組みで、ベンダーに依存しない。
  - ただし、性能カウンターにそのアダプターを使うプロセスが出ているときだけ読む。出ていなければ「休止中」と表示する。
- **理由**: 監視するためのアプリが、監視している対象（電池の消費）を悪くしては意味がないから。

## 5. CPU 温度: 管理者権限なしで取れる範囲にとどめた

- **課題**: CPU 本体（パッケージ）の温度を読むには、MSR などを読むためのカーネルドライバーと管理者権限が要る（HWiNFO や LibreHardwareMonitor と同じ）。
- **決めたこと**: 権限の要らない、ACPI の熱ゾーン（`Thermal Zone Information`）の値を使う。CPU 本体の温度とずれることがある旨を、画面に注記する。
- **理由**: 仕様で「管理者権限は不要」と決めていたから。常駐アプリをドライバーつき・管理者権限で動かすのは、安全面の代償が大きい。

## 6. 更新間隔: 状態ごとに切り替える

```
            ┌──────────────┐ 電源を抜く / 省電力モード ┌──────────────┐
            │  通常        │ ─────────────────────────▶│  バッテリー  │
            │ 時計1秒      │ ◀───────────────────────── │ 間隔を2倍    │
            │ 使用量1秒    │   電源をつなぐ              │ （1〜4倍）   │
            │ 天気10分     │                             └──────┬───────┘
            │ レーダー5分  │                                    │
            └──────┬───────┘                                    │
   全画面のゲーム、 │ ▲ 終わったら、すぐ全項目を1回更新          │
   指定したアプリ   ▼ │                                         ▼
            ┌──────────────┐                           ┌──────────────┐
            │  ゲーム中    │                           │  ロック中    │
            │ 全部止める   │                           │ 全部止める   │
            └──────────────┘                           └──────────────┘
```

- **全画面の判定**: `SHQueryUserNotificationState` だけでは、枠なしの全画面ゲームを拾えないことがある。そこで、前面の窓がモニター全体を覆っているかも確かめる（Chromium と同じ考え方）。
  - デスクトップやタスクバーの窓は除外する。
  - ロック画面も全画面の窓なので、ロック中はゲーム中と数えない。
  - それでも拾えないゲームは、実行ファイル名を登録して、ゲーム扱いにできる。
- **スリープからの復帰**: 状態を見る間隔（2秒）が大きく空いたら、スリープから戻ったとみなして、全項目を更新する。

## 7. 外部データ: 形式の変化に備え、相手に負荷をかけない

- **公式でない API への備え**:
  - 気象庁の警報 JSON とレーダーのタイルは、公式に案内された API ではない。取得先の URL は、すべて設定ファイル `sources.json` に切り出した。
  - 2026年5月に警報の体系が変わった（危険警報＝レベル4の新設、コード表の変更）。新しい形式（r8）に合わせたうえで、知らないコードが来ても「その他の警報・注意報」として表示を続ける。
- **相手への負荷**:
  - レーダーの時刻一覧は、5分より短い間隔では取りに行かない（気象庁は2021年に、アクセスの集中で見にくくなった経緯がある）。
  - タイルは、表示する範囲の分だけを取り、キャッシュする。
- **安全**: 通信先は、`sources.json` に書いたホストだけを許可リストとし、https 以外には接続しない。
- **ブラウザの制約の回避**: 気象庁の JSON は CORS のヘッダーを返さないため、取得は Rust 側で行い、画面には結果だけを渡す。

## 8. 文字の読みやすさ: 色を切り替えるより、ガラスの濃さを調整する

- **課題**: 壁紙の明るさによって、白い文字が読めなくなる。
- **最初の案**: カードの後ろの平均の明るさから、コントラスト比の高いほうの色（白か黒）を選ぶ。
- **実機での問題**:
  - 灰色くらいの明るさでは、どちらの色でも読みにくいのに、黒が選ばれた。
  - 縦に長いカードでは、上と下の明るさが違い、片方が読めなくなった。
- **決めたこと**:
  - 好みの色（白を優先など）は保つ。カードの中で文字にとって条件の悪い側（上位15%の点）でもコントラスト比4以上になるように、そのカードのガラスを必要なぶんだけ暗く（または明るく）する。
  - 上限まで調整しても足りないときだけ、もう一方の色に切り替える。
  - 雨雲レーダーのある天気カードは、地図の上と下を別の領域として判定する。地図の部分は、後ろが見えないので測らない。
- **理由**: 色が頻繁に変わるより、色を保ったまま読みやすくするほうが、利用者の好み（白い文字が見やすい）に合ったから。

## 9. 大きさの変更: 見た目の幅をそろえ、中身ははみ出させない

- **課題**: 全体の倍率とカードごとの倍率を変えると、カードの右端がそろわなくなった。
- **決めたこと**:
  - 見た目の幅を、表示中で最も倍率の大きいカードにそろえる。
  - 倍率の小さいカードは、中身を並べる幅を広げて合わせる。中身の幅が440px（標準の幅）を下回らないので、はみ出さない。
- **検証**: 全体3段階、カードごとの倍率の組み合わせ、デジタル／アナログ、縦1列／横2列の72通りを、自動テストで確かめている。

## 10. 設定の保存: 2つの窓で同期し、壊れないように書く

- **同期**: ガジェットの窓と設定画面の窓は、同じ画面を役割を変えて使う。設定は localStorage と Tauri のイベントで、互いに伝える。設定を読み込んでいる最中の変更は保存し直さないようにして、2つの窓のあいだで保存が往復し続けるのを防ぐ。
- **保存**: 設定ファイルは、一時ファイルに書いてから置き換える（書き込み中に止まっても壊れない）。起動時は、設定ファイルの内容を正とする。
